**草稿 1：Go goproxy 粘住单个子服务器**

链接：https://stackoverflow.com/questions/76362683/why-is-my-go-proxy-server-sticking-to-a-single-child-server-when-sending-request

This is expected behavior for HTTPS, not a bug in your pool — plus one real bug in how you apply the rotation.

For HTTPS, the browser sends one `CONNECT` per origin and then reuses that tunnel (keep-alive). Your proxy only ever sees the `CONNECT` itself; everything after that is encrypted bytes it just forwards. So rotation can only happen per tunnel, not per request: the first `CONNECT` picks a child, and every later request to that origin rides that same child until the tunnel dies. Restarting your servers kills the tunnels, so the next `CONNECT` picks a new child — which then sticks again. That matches your symptoms exactly, including why it "works" for some sites: plain-HTTP requests hit `OnRequest` every time, so they rotate fine.

The real bug in your code: you mutate shared proxy state inside a per-request handler. `proxy.Tr.Proxy` and `proxy.ConnectDial` are globals on the proxy object. Under concurrency that's a data race (Zeke Lu's point stands), and even single-threaded it means tunneled traffic keeps using whatever dialer the last `OnRequest` call set. The rotation logic belongs *inside* those functions, set once at startup:

```go
// Set once at startup. Never reassign these per request.
proxy.ConnectDial = func(network, addr string) (net.Conn, error) {
    child, err := serverPool.GetNextServer() // round-robin, mutex-protected
    if err != nil {
        return nil, err
    }
    return proxy.NewConnectDialToProxyWithHandler(child.String(), nil)(network, addr)
}
proxy.Tr.Proxy = func(req *http.Request) (*url.URL, error) {
    return serverPool.GetNextServer()
}
```

Remove the assignments from `OnRequest` (keep it only for logging if you want), and make sure `GetNextServer` holds `mu` across the pick-and-advance step, or concurrent `CONNECT`s can still return the same child.

How to confirm: log inside `ConnectDial` (child + timestamp) and inside `OnRequest` (method + host). For a sticky site you will see exactly one `CONNECT`, then silence while traffic continues. And compare `http://` vs `https://` through the same proxy: HTTP rotates per request, HTTPS sticks per tunnel.

If you truly need per-request rotation for HTTPS, the proxy cannot do it — the tunnel is opaque by design. Rotate at the client instead (a fresh Puppeteer browser context per batch or site), or accept per-origin stickiness and let rotation happen across origins and reconnects.

**A. Make Squid terminate and re-originate TLS (ssl_bump):**

```
http_port 3128 ssl-bump cert=/etc/squid/squid-ca.pem key=/etc/squid/squid-ca.key generate-host-certificates=on dynamic_cert_mem_cache_size=4MB

ssl_bump peek step1
ssl_bump bump all
tls_outgoing_options cert=/path/to/cert key=/path/to/key cafile=/etc/ssl/certs/ca-certificates.crt
```

You also need to initialize the cert database (`security_file_certgen -c -s /var/lib/ssl_db`), and every client must trust Squid's CA. This is full MITM: it breaks certificate pinning and adds real operational load. Only do it if you truly need Squid to hold the client cert.

    sslcrtd_program /usr/lib/squid/security_file_certgen -s /var/lib/ssl_db -M 4MB
    acl step1 at_step SslBump1
    ssl_bump peek step1
    ssl_bump bump all
    tls_outgoing_options cert=/path/to/cert key=/path/to/key cafile=/etc/ssl/certs/ca-certificates.crt

You also need to initialize the cert database (`security_file_certgen -c -s /var/lib/ssl_db`), and every client must trust Squid's CA. This is full MITM: it breaks certificate pinning and adds real operational load. Only do it if you truly need Squid to hold the client cert.

B. Simpler, and usually right: put the client cert in a component designed for it. For example, an nginx reverse proxy in front of the API with `proxy_ssl_certificate` / `proxy_ssl_certificate_key`, and point your backends at that proxy with plain `http.get()`. Or stunnel in client mode, or keep `--cert`/`--key` in a curl wrapper. If backends must not carry certificates, terminate at a local reverse proxy, not at a forward proxy.

Checks before either path: first confirm the test curl actually goes through Squid — with a proxy, `curl -v` shows the `CONNECT` exchange with the proxy; if it connected to api.example.com directly, your Squid config is irrelevant to that trace. Second, verify the cert and key match (`openssl x509 -noout -modulus` vs `openssl rsa -noout -modulus`), are readable by the squid user, and that the cert file contains the full chain.

**草稿 1：NiFi PutAzureBlobStorage_v12 truststore**

链接：https://stackoverflow.com/questions/80012635/point-nifi-processor-putazureblobstorage-v12-to-custom-truststore

You can't force it — that property doesn't exist for a reason. PutAzureBlobStorage_v12 doesn't use NiFi's HTTP client; it uses the Azure SDK's own HTTP client (Reactor Netty under the hood — your stack trace already shows `reactor.core.Exceptions$ReactiveException`), which builds its TLS context from the JVM default SSLContext. Your SSL Context Service only applies to processors built on NiFi's own client stack, like InvokeHTTP. That's why the property is missing from the Azure processor's docs: there is nothing in that processor to attach the service to.

So the trust has to be fixed at the JVM level, not the processor level. And your worry about cacerts is valid — don't edit the JDK's own cacerts file. Keep your own truststore file and point NiFi's JVM at it:

    cp $JAVA_HOME/lib/security/cacerts /opt/nifi/conf/custom-truststore.jks
    keytool -importcert -alias corporate-proxy -file /path/to/proxy-ca.crt -keystore /opt/nifi/conf/custom-truststore.jks -storepass changeit -noprompt

Then in `$NIFI_HOME/conf/bootstrap.conf`, using the next free `java.arg` numbers:

    java.arg.15=-Djavax.net.ssl.trustStore=/opt/nifi/conf/custom-truststore.jks
    java.arg.16=-Djavax.net.ssl.trustStorePassword=changeit

Restart NiFi. Two details that matter: first, start from a copy of cacerts rather than a truststore containing only the proxy CA, or you'll lose all the public roots and break every other TLS connection. Second, this changes trust for the whole NiFi JVM — which is fine here, since every outbound connection through that intercepting proxy needs the proxy CA anyway. And because the truststore is your own file, JDK updates will never overwrite it — that risk only exists if you edit the JDK's own cacerts.

If you control the proxy, there's a cleaner alternative: exempt the Azure hosts (`*.blob.core.windows.net`) from TLS interception, or let them pass as a plain CONNECT tunnel. Then the SDK does TLS end-to-end with Azure's real certificate, which the JVM already trusts, and no truststore change is needed at all. Interception is the only reason this error exists.

**草稿 2：Cloud Run 直连 IAP Error 11**

链接：https://stackoverflow.com/questions/80013051/google-cloud-run-direct-iap-returns-error-11-after-oauth-consent-with-custom-oauth-client

Error 11 is IAP failing the OAuth handshake against the configured client — in practice, almost always a client ID/secret binding problem, not an application problem. That matches your key observation: the request never reaches Cloud Run, so there is nothing in the application logs to find. IAP rejects it before your code is involved.

Why rotation didn't fix it: rotating the secret in the OAuth client console changes the secret on the OAuth side only. IAP keeps its own stored copy. The "secret fingerprint" shown in the IAP settings is a fingerprint of the stored value — it proves a value is stored, not that it matches the OAuth client's current secret. So a fingerprint match in the console does not rule out a mismatch. The same applies if the secret was rebound at the wrong level (project-level vs the service-level binding that direct Cloud Run IAP actually uses).

What will actually reveal it:

- Check the IAP audit logs, not the application logs. In Cloud Logging, filter for IAP's own entries:

    resource.type="audited_resource"
    protoPayload.serviceName="iap.googleapis.com"

Failed sign-ins show up there with more detail than the user-facing "Error code 11".

- Verify the OAuth client itself in APIs & Services > Credentials: type Web application, status enabled, in the same project as the Cloud Run service, and the authorized redirect URI exactly:

    https://iap.googleapis.com/v1/oauth/clientIds/<YOUR_CLIENT_ID>:handleRedirect

- Isolate client vs binding: create a brand-new Web OAuth client, set the redirect URI above, and bind that client in the IAP service settings. If the new client works, the old client's binding was the problem; if it fails identically, the problem is elsewhere in the IAP setup (consent screen / project state). Testing mode is not itself the problem here, since the account is a listed test user.

On repair: the missing "Auto Generate Credentials" option is expected, not a bug — that option appears in the new-service setup flow, not for an existing direct-IAP service with a custom client. The supported in-place repair is to update the client ID/secret in the service's IAP settings. If the console for this service genuinely doesn't expose those fields, the supported fallback is to toggle IAP off and back on for the service. That does not expose the service publicly: with unauthenticated invocations still disabled, turning IAP off just means requests get an IAM 403 instead of the IAP login screen — and it recreates the OAuth binding without a load balancer or a redeploy.

**标题：** Static Residential IPs for Account Management: What Actually Matters Before You Buy

**标签：** proxy, networking, tutorial, webdev

If you run more than one social media account, you already know the usual advice: vary your behavior, don't spam, warm up slowly. What most guides skip is the network underneath all of it. Platforms don't just watch what you do. They watch where you connect from, and the IP address is the first thing they check.

This guide covers how static residential IPs actually work, how to evaluate one before paying, and the mistakes that get accounts flagged even when behavior looks clean.

## Why the IP comes first

Every account accumulates a fingerprint made of device, behavior, and network. The IP is the most structural part of that fingerprint, and the easiest for a platform to judge:

- A datacenter IP is trivially identifiable. Its ASN belongs to a hosting company, not an ISP, so the platform knows no real household connects from it.
- A shared IP links accounts together. If one account on that IP gets banned for abuse, every other account on the same IP inherits suspicion.
- A residential IP is assigned by an ISP to a household. It looks like ordinary user traffic, which is the whole point.

None of this replaces good behavior. An IP is necessary, not sufficient. But a bad IP can sink an account before behavior even matters.

## Static vs rotating: pick by the job

Rotating proxies give you a new IP per request or per session. That is great for scraping, where volume and distribution matter. It is bad for account management, where consistency matters. An account that logs in from a different city every hour does not look like a person. It looks like a botnet.

A static residential IP stays the same across sessions. The account builds a stable history on one address, which is exactly what long term account nurturing needs. Rule of thumb: scraping rotates, account management stays static.

## The checklist before you buy

**1. Exclusivity.** Dedicated or shared? A shared "residential" IP means someone else's abuse can become your ban. For accounts you plan to keep, dedicated is worth the premium.

**2. Native residential quality.** Check who the IP is registered to. A genuinely residential IP resolves to an ISP's ASN. If the ASN belongs to a cloud provider or a hosting company, it is datacenter traffic wearing a residential label, no matter what the sales page says.

**3. Speed cap vs bandwidth.** Account work is light: posting, messaging, browsing. A 20 Mbps cap with unlimited traffic is plenty for that. Don't pay for gigabit speeds you will never use, and don't confuse a speed cap with a data cap.

**4. Location match.** The IP country, the account's declared region, the device timezone, and the language setting should agree. A US account logging in from a Japanese IP with a Chinese timezone is a mismatch the platform can see.

**5. Term length.** Most providers sell 1, 3, or 6 month terms. Longer is cheaper per month and gives the account a longer stable history. But never buy long before testing: run one IP for a week first and check it actually works for your use case.

**6. History check.** Before committing, check the IP's reputation: fraud score, blocklist status, and whether it was previously used for abuse. A cheap IP with a dirty history is the most expensive kind.

## How to use one in practice

- One identity per IP. At minimum, don't run many accounts through a single address.
- Keep the environment consistent: same IP, same browser profile, same timezone, same language. Consistency is what makes an account look real.
- Don't use a server IP as an account IP. A VPS address is a datacenter address, and it carries all the datacenter disadvantages above. Servers are for tooling, not for logging into accounts.
- Validate small first. One account, one IP, one week. Scale only after that works.

## The pitfalls that keep showing up

- Buying "residential" that is actually datacenter traffic. Always check the ASN.
- Buying "static" that quietly rotates every few days. Test persistence before you trust it.
- Sharing one IP across many accounts to save money, then losing all of them at once.
- Expecting an IP to fix bad behavior. It won't. It only removes the network reason for a ban.

## Bottom line

For long term accounts, the formula is simple: dedicated, static, native residential, location matched, tested before scaling. Get those five right and the network stops being the reason your accounts die.

**标题：GPT-6.1 Terra 能操作电脑了，养号和自动化的规则要变了**

10 月 26 日，OpenAI 发布了 GPT-6.1 Terra。这个模型最值得注意的不是榜单分数，而是它主打的三件事：视觉推理、电脑操作、高频专业任务。它能识别屏幕、调用软件，完成跨应用的工作。换句话说，AI 从只会聊天，变成了会动手。

一、电脑操作意味着什么

以前的自动化分两条路：一条是调 API，一条是写脚本模拟点击。前者要看平台给不给接口，后者脆弱，页面一改就失效。GPT-6.1 Terra 走的是第三条路：直接看屏幕、直接操作软件，跨应用跑完一个流程。门槛一下子低了很多。以前需要程序员写一周的东西，现在可能一句话就能跑起来。

二、对养号和自动化的冲击

冲击分两面。先说好的一面：单人能管的流程变多了，重复性操作可以交给 agent，人的时间回到策略和判断上。再说紧的一面：门槛低了，涌进来的人就多了，平台的风控一定会跟着收紧。风控的逻辑不会变，平台永远在区分人和非人，但识别的重点会变。以前重点看是不是脚本，现在重点会变成操作像不像本人：操作节奏、鼠标轨迹、响应延迟、跨应用的连贯性，这些都会成为信号。agent 操作得越像人，平台就越要找更细的差别。

三、给普通用户的实际建议

第一，别急着用 agent 批量跑号。新工具的红利期，往往也是风控收紧最快的时期，先观望别人的踩坑结果，比自己第一个冲划算。第二，环境一致性比以前更重要。账号、IP、设备、时区、语言，这几项对齐是基本盘，agent 再强也补不上环境露的馅。第三，小规模验证。先拿一个号、跑通一个流程，稳定了再扩。批量之前，先确认这个流程在平台眼里是正常的。

四、和三件套的关系

账号、IP、服务器这三件套的逻辑没变，只是 agent 加入之后分工更清楚了。agent 跑在服务器上，服务器是运行环境，不是账号的身份。账号的出口 IP 还是要走静态住宅 IP，机房 IP 和住宅 IP 在平台眼里是两回事。服务器解决的是 agent 长期在线的问题，IP 解决的是归属问题，两个都对上了，环境才算完整。

结尾

工具在变，规则也在变，但有一条没变：平台永远在找人和非人的分界线。GPT-6.1 Terra 只是把这条线往前推了一步。对普通用户来说，最稳的策略不是追最新工具，而是先把环境做干净，再小规模验证新工具。等 agent 操作的风控尺度明朗了，再决定扩不扩。
