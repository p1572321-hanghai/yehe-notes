```
Chromium never sends proxy credentials preemptively. It only attaches
Proxy-Authorization after the proxy answers with 407 Proxy Authentication
Required. Playwright feeds your username/password into that 407 challenge
(via its request interception) — it does not inject the header into the
first request.

So a blank header on the proxy side means the 407 round-trip never
completed. WebKit's network stack handles proxy auth differently, which is
why the same config works there. This is a Chromium behavior difference,
not a Playwright config error.

1. Check what your proxy actually returns

Run this outside Playwright first:

    curl -v -x http://127.0.0.1:8000 http://httpbin.org/ip

If you don't see a 407 with a Proxy-Authenticate: Basic header, that's
your problem: the proxy is dropping or rejecting the unauthenticated
request (403, connection close, etc.) instead of challenging it, so
Chromium never gets a chance to send credentials. If your proxy is a small
local script, make it return a proper 407. This applies to your plain-HTTP
target too — the proxy still has to challenge with 407.

2. Workaround that sidesteps the challenge flow entirely

Put a small local forwarder between Playwright and your proxy: a proxy
that needs no auth itself, but adds the Proxy-Authorization header when
forwarding upstream (e.g. mitmproxy in upstream mode). Point Playwright
at the forwarder with no credentials. Chromium then has no 407 to answer,
and the header is always present. This is the most reliable fix when you
can't change the proxy's behavior.
```
